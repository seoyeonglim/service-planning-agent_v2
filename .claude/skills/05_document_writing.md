# Skill 05: 문서 작성 노하우

## 목적
읽는 사람이 질문 없이 이해하고 행동할 수 있는 문서를 쓰는 능력.
좋은 기획 문서는 회의 시간을 줄이고 개발 오류를 막는다.

---

## 문서 시작 전 3가지 확인

1. **이 문서의 독자는 누구인가?** (개발자? 대표? 디자이너?)
2. **독자가 이 문서를 읽고 해야 할 행동은 무엇인가?**
3. **결론을 첫 문단에 쓸 수 있는가?**

## 문서 전략

### 기본 원칙
- 결론 우선(Pyramid)
- 한 문장 한 의미
- 추상어 삭제, 수치와 조건으로 대체
- 근거 기반 의사결정 기록(ADR)
- 변경 추적이 가능한 ID 중심 구조
- **PRD 내부 단일 출처**: 값(수치·우선순위·규칙)은 **정본 섹션에 1회만** 쓰고 다른 섹션은 참조한다(PRD가 여러 파일로 분할돼 있어도 세트 전체가 한 문서 — 파일이 달라도 값은 1회다) — 요구사항·우선순위는 `요구사항 레지스트리`, 상세 규칙·수치는 `기능 상세`가 정본. 문제정의·사용자 스토리·엣지케이스는 자기 각도로 **서술**하되 값을 재기술하지 않는다(값 중복 = 나중에 어긋남). 서열·충돌 판정은 CLAUDE.md `PRD 내부 서열`을 따르고, PRD 완료 전 자기 검토는 스킬 15(영역 E)로 수행한다.
- **구현 경계 — 기획서는 기술 문서가 아니다**: 한 문장을 넣기 전에 묻는다 — **"이게 틀리면 사용자·운영자가 겪는 것이 달라지는가?"** 달라지면 기획서, **코드만 바뀌면 개발 문서**다. 개발이 정한 것은 개발 저장소·설계서에 그대로 두고, 기획서는 그 결정이 **① 사용자가 보는 것 ② 우리가 약속할 수 있는 것 ③ 못 지키게 된 것** 중 하나를 바꿀 때만 받아 적는다. 셋 다 아니면 **고치지 않고 링크만 건다.**
  - **쓰지 않는다:** 저장소·제품명(MongoDB 등) · 필드/컬럼·스키마 칸 · API·엔드포인트·버전 번호 · 라이브러리·프레임워크 · 파일명·경로 · 내부 임계값 · 호출 순서·재귀 깊이 · 해시/키·커서·순번 규격 · 컴포넌트 이름(커넥터 등)
  - **쓴다:** 보장되는 결과 · 사용자가 보는 것 · 어긋났을 때 사용자가 겪는 일 · 판정 기준 · 운영 약속(주기·소요·범위·유예)
  - **`결정 로그(ADR)`만 예외**: 방향을 고른 기록이므로 **선택지 이름과 고른 이유까지는** 적는다. 만드는 방법은 여기서도 적지 않는다.
  - **`기능 상세`도 같은 기준이다** — "개발이 무엇을 만드나"가 아니라 **"그 결정이 사용자가 보는 것을 어떻게 바꾸나"**를 쓴다. `엣지케이스`의 `처리 방법`과 `테스트 케이스`의 `Then`도 **관찰 가능한 말**로 쓴다(내부 상태 검사 금지).
  - ⚠️ **신호:** 개발 산출물이 나올 때마다 기획서를 고쳐야 한다면, 기획서가 그 자리를 **너무 세밀하게 쥐고 있다**는 뜻이다. 값 하나를 고칠 게 아니라 **문장 자체를 덜어낸다.** (v1.0 확정 이후엔 그 문장 하나가 CR을 부른다)
- **근거 태그 층위(서사 통제 — CLAUDE.md 공통 규칙의 실행 지침)**: 결정의 시점·경위 태그는 **PRD·ADR까지만**. 하류 문서(UI·기능명세서·화면 HTML·WBS)는 **규칙 내용 + 정본 참조만** — 개정 노트·변경 이력·날짜 태그를 문서 안에 쓰지 않는다. 문서는 **현재 스펙의 정본**이다: "~하기로 했다가"(경위), "(참고) 향후 ~"(가정 해설), "이 표는 ~만 담는다"(자기 해설)는 전부 삭제 대상. 같은 단서를 여러 절에 반복하는 **방어적 반복**도 금지 — 정본 1곳 + 참조로 접는다.
- **가정에는 파급과 검증 방법을 붙인다**: `가정 사항` 각 항목은 **"틀리면 무엇이 바뀌는가(영향 ID) / 언제 참·거짓이 드러나는가 / 누구에게 무엇을 물으면 갈리는가"**를 꼬리표로 단다. 세 번째 칸이 가정을 **액션 아이템**으로 바꾼다 — 확인 상대와 질문이 적히지 않은 가정은 아무도 검증하지 않아 조용히 확정으로 굳는다. 파급이 안 적히는 가정은 실은 미결(❓)이거나 확정(✅)이다. `미결 사항`도 같은 규칙으로 **확인 대상·질문**을 적는다. (WBS 전제의 "미제공 시 후퇴 규칙"과 같은 취지 — 스킬 13)
- **근거 표기(사실·추론 분리 — CLAUDE.md 공통 규칙의 실행 지침)**: 출처 없는 정량 주장·인용·고유명사에는 값 바로 뒤에 마커를 단다.
  - `[출처 필요]` — 어딘가에 답이 있고 확인하면 채울 값 (예: "이관율 12% `[출처 필요]`")
  - `[추정치]` — 우리가 계산·가정한 값. **산출 근거를 괄호로 1줄 병기**한다 (예: "월 8,000건 `[추정치 — 일 평균 260건 × 30일]`")
  - 마커는 **초안(v0.x) 한정**이다. v1.0 확정 전에 ① 출처 표기 ② `가정 사항`·`미결 사항` 이관 ③ 삭제 중 하나로 전부 해소한다(잔존은 `consistency_check.py`가 확정 상태에서 ❌).
  - 하류 문서(UI·기능명세서·WBS)에는 마커를 옮겨 적지 않는다 — 근거는 PRD가 정본이고 하류는 확정된 값만 받는다(`근거 태그 층위`와 같은 원리).
- **빈칸은 채우지 않는다**: 사용자가 말하지 않은 범위·대상·조건·수치는 문맥상 그럴듯해도 쓰지 않는다. 템플릿의 어떤 칸이 비었다는 사실 자체가 정보다 — 채우고 싶으면 `AskUserQuestion`으로 되묻고, 답이 없으면 `미결(❓)`로 남긴다. **모든 칸이 채워졌지만 앞뒤가 어긋나는 문서**가 빈칸이 보이는 문서보다 나쁘다.
- **문서 정보 헤더 최소 세트**: `문서 버전 / 상태 / 작성일(최초 YYYY-MM-DD · 최종 YYYY-MM-DD) / 선행·근거 문서 / 범위·목적`만 둔다. **내용을 수정할 때마다 '최종' 날짜를 갱신**한다(수정 마감 체크에 포함). 개정 노트·변경 이력은 헤더에 두지 않는다(추적은 git 커밋 — 확정 baseline 이후는 CR).

## 독자별 문서 전략

| 독자 | 강조할 것 | 생략할 것 | 분량 |
|------|-----------|-----------|------|
| 개발자 | 조건, 예외, 데이터 형식 | 비즈니스 배경 | 상세하게 |
| 대표/클라이언트 | 임팩트, 수치, 일정 | 기술 세부사항 | 1페이지 요약 |
| 디자이너 | 사용자 감정, 플로우, 상태 | 비용, 공수 | 플로우 중심 |

## PRD 파일 구성 — 단일 파일로 시작, 임계 초과 시 3분할

PRD는 기본적으로 `prd/PRD.md` **한 파일**로 쓴다. 문서가 커져 아래 임계를 넘으면 **읽는 사람 축**으로 3개 파일로 쪼갠다. 파일만 나뉜 것이지 **한 문서**다 — 서열·단일 출처·근거 표기 규칙이 그대로 적용된다.

**분할 임계(둘 중 하나라도 넘으면):** `PRD.md` 600줄 초과 · TC 15건 초과

| 파일 | 담는 섹션 | 주 독자 |
|---|---|---|
| `prd/PRD.md` | 문서 정보 · 한줄 요약 · 문제 정의 · 사용자 정의 · **요구사항 레지스트리** · 스코프 · 사용자 스토리 · NFR · 결정 로그(ADR) · 가정/확정/미결 · 변경 이력 · 관련 문서 추적 | 고객·경영·기획(의사결정) |
| `prd/PRD_기능상세.md` | 기능 상세(REQ별 정상 플로우·예외 처리·연계 기능) · 핵심 플로우 Mermaid | 개발·기능명세(FS) 입력 |
| `prd/PRD_검증.md` | 엣지케이스(`EC-##`) · 테스트 케이스(`TC-###`) | QA |

- **엣지케이스와 TC는 한 파일로 묶는다** — TC 헤딩이 EC를 직접 참조하므로(`### TC-003 (REQ-012, EC-01)`) 떼어 놓으면 매번 두 파일을 오가게 된다.
- **요구사항 레지스트리는 `PRD.md`에 남긴다** — 스코프·우선순위와 함께 읽히는 정본이고, 계약·리뷰의 중심이다.

### 분할 시 반드시 지킬 제약

1. **세 파일 모두 `prd/` 폴더 안에 둔다.** `validate_traceability.py`·`consistency_check.py`는 `prd/*.md`를 **이어붙여** 읽는다 — 폴더를 벗어나면 MUST REQ의 TC 커버리지·EC 참조 검사가 통째로 깨진다. 파일명은 `_`로 시작할 수 없고 `CHANGELOG.md`도 쓸 수 없다(둘 다 스크립트가 리포트·변경기록으로 보고 본문에서 제외한다).
2. **`상태:` 줄은 `PRD.md`에만 둔다.** 분할 파일의 문서 정보는 `> 정본: PRD.md — 이 파일은 PRD 세트의 일부다` 한 줄로 대신한다. baseline 판정이 `prd/*.md` 전체에서 '확정'을 찾기 때문에, 분할 파일이 다른 상태를 들고 있으면 확정 여부를 오판한다(초안 한정 마커 잔존 검사가 잘못 걸리거나 잘못 통과한다).
3. **헤딩 형식은 그대로 유지한다.** REQ 선언은 `요구사항 레지스트리` 헤딩 하위에서, EC·TC 선언은 `### EC-01`·`### TC-001` 헤딩 패턴으로 인식된다. 이 형식만 지키면 파일이 나뉘어도 스크립트 수정은 필요 없다.
4. **값 중복 금지는 파일이 나뉘어도 동일하다.** 값(수치·우선순위·규칙)은 정본 1곳에만 쓰고 다른 파일은 참조한다. 파일이 갈라졌다는 이유로 "여기도 적어 두면 편하니까" 복사하는 순간 두 파일이 어긋나기 시작한다.
5. **`PRD.md`의 `관련 문서 추적`에 분할 파일 경로를 적는다.** 하류 문서·다음 세션이 PRD 세트로 들어오는 진입점이다.

### 분할 시점

- **초안(v0.x):** 임계를 넘은 것을 확인한 자리에서 쪼개고 git 커밋 1건으로 남긴다(CR 불필요).
- **v1.0 확정(baseline) 이후:** 구조 변경이므로 CR 1건을 남긴다 — AS-IS/TO-BE는 문구 인용이 불가능하므로 전/후 **파일 구성**을 서술한다. 이때 내용은 한 글자도 바꾸지 않는다(내용 변경은 별도 CR).
- **제품 축 분할과 곱하지 않는다.** 이미 제품별로 PRD가 나뉜 프로젝트(`PRD_platform.md`·`PRD_assistant.md` …)는 개별 제품 PRD가 임계를 넘을 때 **그 제품에 한해** 검증층을 뗀다(`PRD_platform_검증.md`). 3제품 × 3섹션 = 9파일로 불리지 않는다.

## 변경 기록(CR) 작성 규칙 — v1.0 확정 이후 필수

v1.0 확정(baseline) 이후의 모든 변경은 `docs/[프로젝트명]/prd/CHANGELOG.md`에 CR(Change Record) 1건으로 기록한다.
목적: **대상 / 변경 전 문구(AS-IS) / 변경 후 문구(TO-BE) / 변경 범위 / 사유 / 승인** 6항목이 한 레코드에서 한눈에 보이게 한다(변경 날짜는 CR 헤딩에 기재).

- CR은 실행 기록, ADR은 의사결정 기록이다. 방향성 결정이 동반되면 ADR을 먼저 남기고 CR의 사유 칸에서 링크한다(ADR 1건 : CR N건 가능).
- **AS-IS/TO-BE는 문구를 그대로 인용**한다(요약 금지 — 구조 변경처럼 인용이 불가능한 경우만 전/후 상태를 서술).
- **변경 범위는 3단계로 작성한다:**
  1. `python3 .claude/scripts/impact_scan.py [대상ID] --md` 실행 → 대상 ID가 등장하는 파일 체크리스트가 자동 생성됨
  2. 체크리스트의 각 파일을 열어 수정 필요 여부를 확인하고, 고친 곳은 체크·"영향 없음"인 곳은 사유와 함께 기록
  3. `python3 .claude/scripts/validate_traceability.py`로 유령/고아 오류가 없는지 재확인
- CR 없이 v1.0 이후 문서를 수정하는 것 금지.
- 변경 요청이 자연어로 들어왔을 때의 전체 절차(REQ ID 매핑 확정 → 영향 스캔 → 변경안 승인 → 파일별 컨펌 수정)는 `14_change_request.md`를 따른다. 이 섹션은 그 결과를 CR 레코드로 남기는 형식 규칙이다.

```markdown
### CR-003 | 2026-07-07 | REQ-041 보험료 재계산 조건 변경

| 항목 | 내용 |
|------|------|
| 대상 | REQ-041 (+ 연쇄: SC-05, FS-012, TC-018) |
| AS-IS | "사용자는 설계 화면에서 나이·성별 변경 시 보험료를 재계산할 수 있다" |
| TO-BE | "사용자는 설계 화면에서 나이·성별·납입기간 변경 시 3초 이내 보험료를 재계산할 수 있다" |
| 변경 범위 | PRD §7 기능상세, 화면명세 SC-05 입력규칙, 기능명세 FS-012 처리규칙, 테스트 TC-018 Then절, WBS W04(영향 없음 확인) |
| 사유 | ADR-07 참조 — 고객사 6/23 방향성 변경 미팅에서 납입기간 슬라이더 요구 |
| 승인 | 사용자 확인 2026-07-07 |
```

## Mermaid 플로우차트 작성 규칙

반드시 이 순서로 작성해라:
1. 정상 플로우 (happy path) 먼저
2. 분기점마다 조건 명시
3. 오류/예외 플로우 별도 표시
4. 각 단계에 액터 명시 (고객 / 상담사 / 시스템 / 외부 연동)

## 문서 완성 후 자가 검토 (발행 전 필수)

- 처음 보는 개발자가 질문 없이 구현할 수 있는가?
- 대표가 30초 안에 핵심을 파악할 수 있는가?
- 확정/가정/미결이 구분되어 있는가?
- **가정·미결마다 확인 대상과 질문이 적혀 있는가?** (없으면 아무도 검증하지 않는다)
- **정량 주장에 출처가 붙었거나 마커(`[출처 필요]`·`[추정치]`)가 달렸는가?** — 확정본이면 마커가 0건이어야 한다
- **사용자가 정하지 않은 것을 우리가 채워 넣은 문장은 없는가?** (범위·대상·조건·수치)
- **왜 하는가(문제·성공 기준·do-nothing)가 어떻게 만드는가보다 먼저 채워졌는가?**
- **개발이 내일 방식을 바꿔도 이 문장이 그대로 유효한가?** — 아니면 그 문장은 개발 문서 몫이다(구현 경계). 저장소·필드·API·파일명·임계값·호출 순서가 본문에 있으면 지운다
- 스코프 안/밖이 명시되어 있는가?
- 모든 기능이 REQ-###로 식별되는가?
- 모든 기능의 엣지케이스와 테스트가 연결되어 있는가?
- **분량이 분할 임계(600줄·TC 15건)를 넘었는가?** 넘었으면 `PRD.md` / `PRD_기능상세.md` / `PRD_검증.md`로 쪼갠다 — 분할 후 `상태:` 줄이 `PRD.md`에만 있는지, `관련 문서 추적`이 분할 파일을 가리키는지 확인한다
- 추상적 표현이 없는가? ("간편한", "빠른" 등)

하나라도 No면 즉시 수정한다.
