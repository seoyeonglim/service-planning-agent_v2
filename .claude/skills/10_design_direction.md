# Skill 10: 디자인 방향 (Design Direction)

## 목적
기획된 사용자 플로우와 화면을 일관된 시각 체계로 바인딩한다.

---

## 이 스킬의 범위 — 디자인 시스템이 이미 정한 것은 다시 정하지 않는다

시각 규칙의 정본은 `.claude/design-system/`(AX팀 디자인 시스템 vendoring)이다. **토큰은 상속해 쓰는 것이지 새로 만드는 게 아니다**(`getting-started.md`).

| 이미 정해져 있는 것 | 정본 | 이 문서에서 |
|---|---|---|
| 색·타이포·radius·shadow·spacing 값 | `design-system.md` | **새로 정하지 않는다.** 어떤 semantic 토큰을 어디에 쓰는지만 적는다 |
| 버튼·카드·입력·배지 스타일 | `component-variants.md` | **새로 정하지 않는다.** 필요한 컴포넌트를 나열한다 |
| 여백·위계·인터랙션·접근성 기준선 | `design-playbook.md` 0~9 | **새로 정하지 않는다.** 편차가 필요하면 사유와 함께 기록한다 |
| 화면 골격(아키타입 잠금 규칙) | `layout-types/*.md` | **새로 정하지 않는다.** 판별 결과와 편차를 기록한다 |

- **AVOID 팔레트 표에 hex 코드를 새로 적지 않는다.** 화면 HTML의 하드코딩 색은 `check-design-tokens.mjs`가 ERROR로 잡는다 — 이 문서가 게이트가 차단할 값을 지시하는 문서가 되면 안 된다.
- **RULE 이 문서가 정하는 것은 「디자인 시스템이 답을 주지 않는 것」뿐이다** — 대상 기기, 도메인 용어·아이콘, 밀도 선택, 그리고 **아키타입 잠금 규칙에서 벗어나는 편차와 그 사유**.
- 정본 값을 바꾸고 싶으면 이 레포에서 고치지 말고 정본 소유자에게 제안한다(CLAUDE.md `디자인 검증`).

## 실행 프로토콜

### Step 0: 화면 유형 판별 (가장 먼저 · 생략 금지)

Read `.claude/design-system/layout-types/00-type-selection.md` 후 네 질문으로 유형을 가른다.

- **RULE 사용자가 유형을 명시하지 않아도 수행한다.** 지시가 없는 것이 생략의 근거가 되지 않는다.
- **RULE 잘못된 유형으로 완성된 화면은 토큰이 전부 맞아도 다시 만들어야 한다.**
- 유형이 **워크스페이스**면 `01-workspace.md` 0.5절의 **3축**(자료 소재 · 결과 갯수 · AI 대화 역할)을 PRD에서 채우고 매트릭스를 조회해 아키타입을 정한다. **감으로 고르지 않는다.**
- 유형이 **어드민**이면 `02-admin.md`를 추가로 받아 LNB 메뉴 × 페이지 타입 매핑을 산출물로 삼는다(3축을 묻지 않는다).
- **RULE 판별 결과(유형 · 아키타입 · 축 답변)를 문서 첫 섹션에 표로 남긴다.**

### Step 1: 필수 정보 수집 질문

**디자인 시스템이 답을 주지 않는 것만** 묻는다. 색·타이포·컴포넌트 스타일은 이미 정본에 있으므로 묻지 않는다.

1. "주요 사용 환경은?" → PC / 태블릿 / 모바일 중 **기준 1개 확정**
2. "아키타입 잠금 규칙과 어긋나는 화면 구성이 있는데, 그대로 갈까요?" → **편차 승인**(Step 0에서 충돌이 발견됐을 때만)
3. "이 도메인에서만 쓰는 용어·아이콘·상태 표현이 있나요?" → 도메인 특이성
4. "참고하고 싶은 서비스가 있나요?" → 레퍼런스. **단, 레퍼런스는 골격·상호작용을 참고하는 용도지 색을 가져오는 용도가 아니다.**
5. "이 화면을 쓰기 어려운 조건이 있나요?" → 저시력·색각이상, 키보드 전용, 소음·장갑, 구형 브라우저, 장시간 응시 등. 답을 **「이 프로젝트가 정하는 것」의 `사용 환경 제약`** 행으로 남긴다.
   - **RULE 여기서 정하는 것은 「누가 어떤 환경에서 쓰는가」뿐이다.** 대비비·타깃 크기·모션 같은 **수치 기준은 `design-playbook.md` 1.6·1.8·1.9가 정본**이므로 이 문서에서 재선언하지 않는다(스킬 16 접근성 렌즈).

질문 없이 디자인 방향을 임의로 결정하지 말 것. 선택지가 있는 질문은 `AskUserQuestion`을 쓴다.

### Step 2: 상속 확인 + 재량 기록

새로 정의하지 말고, **무엇을 상속하고 무엇이 재량인지**를 표로 확정한다.

- **상속:** 컬러 토큰(어떤 semantic 토큰을 어떤 용도에), 타이포 27토큰 중 사용 범위, spacing 스케일, 컴포넌트 variant 목록
- **재량:** 대상 기기·최대 너비, 도메인 용어·아이콘, 밀도(compact/기본), 아키타입 편차
- **금지:** hex 값 신설, raw Tailwind 타이포(`text-sm` 등) 지시, 임의 고정 치수 지시

### Step 3: 결정 로그(ADR) 남기기

디자인 결정 시 대안 1개 이상 기록:

- 채택: 왜 이 구성인지
- 거절: 왜 다른 구성은 배제했는지
- 영향: 어떤 페르소나에 유리한지
- **아키타입 편차는 반드시 ADR로 남긴다** — `00-type-selection.md`의 "기록이 곧 게이트다" RULE.

## 산출물 구성 (`ui/04_design_direction.md`)

```markdown
## 1. 화면 유형 판별
| 항목 | 판정 | 근거 |
(유형 · 3축 답변 · 아키타입 · 검증 케이스)

## 2. 아키타입 잠금 규칙 대조
| 잠금 규칙 | 우리 화면 | 판정 |
(준수 / 편차+사유. 편차는 ADR 링크)

## 3. 상속하는 것 (디자인 시스템 정본)
| 영역 | 정본 | 이 프로젝트에서의 사용 범위 |

## 4. 이 프로젝트가 정하는 것
| 항목 | 결정 | 사유 |
(대상 기기 · 최대 너비 · 도메인 용어·아이콘 · 밀도 · 사용 환경 제약)

## 5. 화면별 적용 지시 (SC-## 기준)
| SC-## | 아키타입 구역 | 필요한 컴포넌트 | 비고 |

## 6. 결정 로그(ADR)
```

## 체크리스트

- **화면 유형과 아키타입이 판별 절차대로 정해졌는가?** (감으로 고르지 않았는가)
- **아키타입 잠금 규칙을 항목별로 대조했고, 편차마다 사유가 적혔는가?**
- **새로 정의한 hex·raw 타이포·임의 치수가 0건인가?** (있으면 게이트가 차단한다)
- 모바일/태블릿/PC 기준 중 1개가 확정되었는가?
- `요청사항 ID(REQ-###)`·`SC-##`와 UI 적용 지시가 연결되었는가?
- **사용 환경 제약(접근성 전제)이 「이 프로젝트가 정하는 것」에 기록되었는가?** (스킬 16 — 수치 기준은 `design-playbook.md` 정본)
- 각 페르소나의 사용성 조건과 충돌 여부 점검
