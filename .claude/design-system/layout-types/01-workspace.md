# 레이아웃 유형 가이드 — ① 워크스페이스 / 툴

**대상:** Claude (PoC 제작 시 컨텍스트로 주입)
**역할:** "올리면 AI가 처리해서 결과를 보여주는" 화면을 만들 때의 **아트디렉션 브리프**. 규칙집이 아니라 "이렇게 보여라 / 이렇게 하지 마라".
**관계:** `design-system.md`(토큰 값) + `design-playbook.md`(공통 레이아웃·접근성·상태)를 **상속**한다. 이 문서는 그 위에 얹는 **워크스페이스 유형 전용 층**이다. 토큰·접근성·4상태 등 공통 규칙은 여기서 반복하지 않는다.
**버전:** v0.6 (2026-08-03 · 아키타입 A(세로 스택형) 폐기 — 예시 화면 없는 미검증 가설이라 dana 요청으로 제거, A/B 를 가르던 부축(입력 밀도)도 함께 제거)
**shadcn 강제력:** **RULE** — 필요한 primitive 는 `pnpm dlx shadcn@latest add <name>` 로 추가해서 재사용. 커스텀은 shadcn 에 없는 것(차트·차트 트레이스·챗 버블 등) 이나 도메인 특이 시각화(스팟 일러스트) 에만 한정. 커스텀 추가 시 dana 문의.
**근거 레퍼런스 (레포 밖 자산 — 피그마·디자이너 로컬 보관, 이 레포에서 열리지 않는다):** ref-danal-bi.png, ref-doowon-mobility.png, ax-seragem-demo(코드). 랜딩 참고: ext-extend.png·ext-docsumo.png(제품이 강조하는 것만 참고, 레이아웃 아님).
**검증 케이스 (PoC 로 이 MD 검증한 것):**
- 두원 mobility (아키타입 B · 좌우 분할) — `src/app/experiments/workspace-doowon-poc1/` ([정본 레포에서 보기](https://github.wrtn.club/wrtn-tech/ax-design-system/tree/develop/src/app/experiments/workspace-doowon-poc1))
- 다날 데이터 에이전트 (아키타입 C · 대화 주도) — `src/app/experiments/workspace-danal-poc1/` ([정본 레포에서 보기](https://github.wrtn.club/wrtn-tech/ax-design-system/tree/develop/src/app/experiments/workspace-danal-poc1))

> 위 `src/app/experiments/...` 는 **정본 레포 기준 경로**다. 이 문서를 vendoring 해 간 레포에는 그 화면이 없으므로, 확인이 필요하면 옆의 웹 링크로 연다.

> 강제력 어휘는 playbook과 동일 — **RULE**(반드시) / **PREFER**(권장 기본, 디자이너 보정 가능) / **AVOID**(하지 말 것).

## 0. 이 유형인지 판별 (먼저 확인)

- **맞음:** 사용자가 **뭔가를 입력(업로드·질의)하면 AI가 처리해서 결과물을 만들어 보여주는** 화면. 화면의 주인공 = **방금 만들어진 결과물**. 일회성 태스크.
- **아님 → 어드민/콘솔:** 여러 건을 목록·테이블로 관리·운영하는 화면(주인공 = 쌓인 데이터).
- 섞이면 **주된 일**로 분류. 워크스페이스에 작은 작업이력 테이블이 붙는 건 정상(주인공은 여전히 결과).

## 0.5 판별 축 — 아키타입 선택의 근거 (v0.3 신설)

> 0번에서 워크스페이스로 판별됐다면, **감으로 아키타입을 고르지 말고** 아래 3개 축의 조합으로 판별하라. 감으로 고르면 두원/다날 사례처럼 시각적으로 같아진다 (둘 다 "좌 패널 + 우 캔버스" 로 수렴).

### 축 1 — 자료 소재 (data locus)
- **유저-업로드형:** 유저가 매번 다른 자료를 올린다 (사진·파일). 그 자료가 화면에 **상시 참조** 되어야 워크플로우가 성립. → 좌 패널에 자료 원본 필요.
- **시스템-상시형:** 자료는 백엔드에 이미 존재. 유저는 데이터 자체를 몰라도 됨. 화면에 자료 원본을 노출할 이유가 없음. → 좌 패널 자리에 다른 것(대화 목록 등)이 옴.

### 축 2 — 결과 갯수 (result cardinality)
- **1건 고정:** 한 세션 = 하나의 결과물. 편집·저장까지 그 하나에 집중. → 캔버스는 "그 하나" 에 집중.
- **N건 누적:** 매 대화·요청이 새 결과 생성. 이전 결과도 스크롤 위에 남아 **계보(lineage)** 형성. → 캔버스는 세로 스트림.

### 축 3 — AI 대화 역할 (chat role)
- **부가 조력자:** 결과는 이미 만들어짐. 대화는 그 결과를 해석·검증. **대화 없어도 프로덕트 성립.** → 사이드 슬라이드 패널 (열림/닫힘 토글).
- **주 엔진:** 결과가 대화로만 생성됨. 대화 = 워크플로우 그 자체. **대화 없으면 결과 자체가 없음.** → 하단 sticky composer 상시 노출.

### 축 조합 → 아키타입 매트릭스

| 축1 자료 | 축2 결과 | 축3 대화 | → 아키타입 | 검증 케이스 |
|---|---|---|---|---|
| 유저-업로드 | 1건 | 부가 | **B** (좌우 분할) | 두원 mobility |
| 시스템-상시 | N건 누적 | 주 엔진 | **C** (대화 주도) | 다날 데이터 에이전트 |

**폐기 이력 (v0.6):** 같은 축 조합에서 부축(입력 밀도)이 낮으면 **A (세로 스택)** 로 가르던 행이 있었으나, 예시 화면 없는 미검증 가설로만 남아 폐기했다 (dana 요청). 세로 스택 골격이 필요해 보이는 케이스가 오면 dana 와 상의.

### 판별 프로세스 (PRD 받으면 이 순서로)

1. PRD 데이터 흐름 확인 → **축1** 답변 (유저가 자료 올리나?)
2. PRD 워크플로우 종결점 확인 → **축2** 답변 (결과가 몇 개?)
3. PRD 에서 LLM 이 뭘 하는지 확인 → **축3** 답변 (대화가 결과를 만드나, 해석하나?)
4. 위 3개 답 → **매트릭스 조회** → 아키타입 자동 결정
5. 아키타입 잠금 규칙(1번 섹션) 조회 → 화면 뼈대 대부분 자동 결정
6. **shadcn 감사** — 필요한 primitive 리스트업 → `src/components/ui/` 에 있는지 확인 → 없으면 `pnpm dlx shadcn@latest add <name>` 으로 설치. 있는데 안 쓴 것도 있으면 사용으로 전환. **커스텀 (raw `<input>`·`<table>`·`<div>` 등) 은 shadcn 에 진짜로 없는 것에만 한정**.
7. 남은 재량은 **도메인 특이성**(색·용어·아이콘·엣지 케이스) 에만

### 판별과 별도 · PoC 커버리지 (v0.5 신설 RULE)

- **RULE 하나의 PoC 는 대표 유저 플로우 상태를 모두 커버.** 최소 **진입(Empty/Upload/Welcome)** 화면 + **결과(Active/Result)** 화면. 가능하면 **처리 중(Processing/Loading)** 화면까지.
- 감으로 "결과 화면 하나만" 뽑고 넘어가면 안 됨 — 실제 유저는 진입점부터 시작하고, 다른 팀원이 이 MD 를 재사용할 때는 진입 화면 없으면 흐름을 못 그림.
- **판별 근거:** 실 앱 코드(`repo/*/components/*` · 라우트 흐름)를 읽어서 대표 상태를 나열 → 각각 시안 뽑기.
- **검증 러닝 (2026-07-30):** 두원 첫 시안 · 세라젬 첫 시안이 결과 화면만 뽑아 dana 가 매번 "진입 화면도 해줘" 라고 요청해야 했음. 회고 반영 후 규칙 신설.

## 1. 레이아웃 아키타입 (둘 중 골라 변주 — 흐름·비중은 고정)

> 매번 같은 와이어프레임 금지. 아래 2개 중 콘텐츠에 맞는 걸 고르고, 그 안에서 자유롭게 변주한다. **고정은 "흐름(입력→처리→결과)과 결과 우선 비중"뿐.**
>
> ⚠️ **이 2종은 "잠긴 와이어프레임"이 아니라 기존 PoC에서 관찰된 "출발점(가설)"이다.** PRD가 요구하는 기능에 따라 구역·구성이 달라지는 게 정상 — 아키타입은 시작점일 뿐, PRD 기능이 우선한다. **확정이 아니라 테스트(실제 PRD 1건을 이 MD로 생성)로 검증할 대상.** (playbook 4.1 랜딩이 "와이어프레임 미리 못박기" 때문에 재검토된 것과 같은 교훈)

### B. 좌우 분할형 — *(두원 mobility 검증)*
```
[좌: 설정·업로드 패널]  |  [우: 결과 캔버스 (크게)]
   양식·카테고리·권한          미리보기 + 편집
```
- **축 조합:** 유저-업로드 + 1건 + 부가.
- **PREFER** 설정 옵션이 많거나, 업로드와 결과를 동시에 보며 조정할 때. 좌 패널 `PREFER 360~400px` (playbook 4.3 워크스페이스 폭 상속).

**잠금 (RULE — 두원 PoC 검증):**
- **RULE** 좌 패널 = **자료 원본 + 처리 상태 + 메타 정보**. 대화 목록·설정 트리 등 다른 용도 금지. 자료가 상시 참조되어야 축1(유저-업로드) 정체성 성립.
- **RULE** 우 결과 = **편집 가능한 표/컴포지션**. 뷰만 있는 결과는 이 아키타입이 아니다 (맞는 골격은 미정 — dana 와 상의). 편집이 이 아키타입의 워크플로우 완결점.
- **RULE** AI 대화는 **사이드 슬라이드 패널 (열림/닫힘 토글)**. 상시 노출·좌 패널 대체 금지 — 대화가 주 엔진이 되는 순간 축3 위반 → C로 이동.
- **RULE** 하단 sticky 액션바 = **편집·저장·다운로드**. "다음 질문 인풋" 아님 (그건 C).
- **RULE** 결과 캔버스 안 셀·필드는 **신뢰도 배지**(high·mid·low) 로 검토 우선순위 표시. 편집이 워크플로우니까 어디 봐야 할지 안내 필요.

**두원 검증에서 확인:** OCR 결과 표 편집 + DB 커밋이 워크플로우 완결. 우측 AI 슬라이드 패널이 "왜 이래?" 질문용으로 부가. 대화 없어도 프로덕트 성립. `<DailyReportSketch />` 처럼 도메인 특이성(shop-floor 필기 일보) 은 좌 패널 자료 자리에.

**B 아키타입 shadcn 매핑 (v0.4 반영):**
- 편집 가능 표 → `Table` + `TableHeader/Body/Row/Cell` + `Card` (외곽)
- Stat 카드 → `Card` (with p-5)
- AI 대화 예시 질문 버튼 → `Button variant='outline'`
- AI 대화 인풋 → `Input` (내부 pill 컨테이너는 커스텀 조합)
- 도메인 특이(스팟 SVG 일러스트) → 커스텀 정당

### C. 대화 주도형 — *(다날 데이터 에이전트 검증)*
```
[좌: 대화 목록 사이드바 (상시 노출 · 256~280px)] | [우: 캔버스]
                                                    ├ Turn 1 [유저 발화 우측 버블 · AI 응답 좌측 · 결과 아티팩트]
                                                    ├ Turn 2 [유저 발화 · AI 응답 · 결과 아티팩트]
                                                    ├ Turn 3 [현재 초점 · 상세]
                                                    └ [하단 sticky composer: 다음 자연어 질문]
```
- **축 조합:** 시스템-상시 + N건 누적 + 주 엔진.
- **PREFER** 입력이 자연어이고 결과가 데이터 시각화·리포트일 때. 챗봇과 달리 **주인공은 대화가 아니라 생성된 결과물** — 대화는 결과 생성 엔진.

**잠금 (RULE — 다날 PoC 검증):**
- **RULE** 좌 사이드바 = **대화 목록 상시 노출** (256~280px). 접힘·드로어 토글 금지 — 대화 세션 접근이 워크플로우 진입점. 로고·새 대화 버튼·검색·유저 메뉴도 이 사이드바 안에 통합.
- **RULE** 캔버스 = **결과 계보 세로 스트림**. Turn 1·2·3 각각이 완전한 결과 아티팩트(차트·표·인사이트)로 세로 누적. Turn 하나만 크게 보여주고 나머지를 chip 으로 압축 금지 → 축2(N건 누적) 정체성 훼손.
- **RULE** 유저 발화 = **우측 정렬 muted 버블** (`rounded-2xl rounded-tr-sm`, `bg-surface-secondary`). AI 응답 = 좌측 정렬 (스파클 아이콘 + 메타 + 타이틀 + 결과 아티팩트). 챗 관습(유저 우/AI 좌) 로 turn 경계가 시각적으로 즉시 잡힘.
- **RULE** AI 응답 헤더에 **"완료" status 배지 금지** — 응답 도착 = 완료 자명. 배지는 처리중·에러 등 non-default 상태에서만.
- **RULE** turn 사이 divider 금지 — 유저 버블 우측·AI 응답 좌측 대비만으로 경계 충분. bg 밴드·`border-t` 금지 (섹션 구분 규칙 3.1 상속).
- **RULE** 하단 sticky = **다음 자연어 질문 인풋**. 결과 편집 액션 아님.
- **RULE** 자료 원본 패널 금지. 축1 = 시스템-상시. 자료가 상시 참조 필요 없으니 그 자리에 대화 목록 사이드바가 옴.
- **RULE** 상단 topbar = **얇게, 현재 대화 제목만**. breadcrumb·툴바 오버스펙 금지.

**다날 검증에서 확인:**
- 첫 시안: Turn 3만 크게 보여주고 Turn 1·2 를 chip 압축 → 두원과 시각적으로 동일해짐 ("거의 똑같네" 지적) → 3개 turn 세로 스트림으로 재구성 후 정체성 살아남.
- 두 번째 시안: 좌 사이드바를 드로어로 접음 → 두원의 "좌 패널 + 우 캔버스" 구조와 겹침 → 상시 노출로 되돌림.
- 세 번째 시안: 유저 발화 좌측 정렬 → turn 경계 불명확, divider 필요 → 우측 muted 버블로 전환 후 divider 없이도 경계 명확.

**C 아키타입 shadcn 매핑 (v0.4 반영):**
- 결과 상세 표 → `Table` + `Card` (외곽)
- 결과 카드 (차트·인사이트·트레이스) → `Card`
- Composer 인풋 → `Input` (내부 pill 컨테이너는 커스텀 조합)
- Composer 전송 버튼 → `Button size='icon' className='rounded-full'`
- 좌 사이드바 대화 아이템 → `SidebarItem` (state='current'|'default')
- 좌 사이드바 검색 인풋 → `Input` (with leading `Search` 아이콘)
- 좌 사이드바 하단 유저 → `Avatar` + `AvatarFallback` (initial)
- 도메인 특이(차트 SVG, 유저 발화 muted 버블) → shadcn 미존재로 커스텀 정당

## 2. 시그니처 무브 (이 유형을 "이 유형답게" 만드는 구체 동작)

- **RULE 처리 상태를 항상 명시** — `Empty(입력 대기) → 처리중(진행률/스트리밍) → 완료`. 처리 과정을 숨기지 말 것. 결과가 스트리밍이면 실시간으로 채워라. (playbook 1.7 4상태 상속)
- **RULE 결과 캔버스가 화면의 주인공** — 결과 영역이 가장 큰 비중. 입력·설정은 간결하게(상단 카드 또는 좌측 패널).
- **PREFER 결과를 원문 맥락 위에** — 원문 ↔ 추출결과를 **좌우 나란히**(DP COMPOSE) 두거나, 원문 위에 **배지·하이라이트로 오버레이**(Rossum·Extend식). AI 산출물은 근거와 함께 보여 신뢰를 만든다.
- **PREFER 결과 품질을 수치로** — 신뢰도·정확도·상태를 배지/미터로 노출(Extend 95.7%, Docsumo 실시간 스코어). "얼마나 믿어도 되나"를 사용자가 알게.
- **PREFER 결과에 대한 후속 동선** — 편집(셀·컬럼 수정), 다운로드(JSON/xlsx), 결과에 대한 AI 질문 패널. 결과를 "보고 끝"이 아니라 "이어서 작업".
- **PREFER 입력 진입은 크고 분명하게** — 파일형은 큰 드래그&드롭 존, 자연어형은 눈에 띄는 질의창. 무엇을 넣어야 하는지 즉시 알게.

## 3. 보이는 값 (우리 DS 기준 — 색은 semantic 토큰만)

- **RULE 라이트/다크 모드 전환 제공** — DS가 양모드 토큰을 완비했으므로 상단바에 모드 토글을 둔다. semantic 토큰만 쓰면 자동 대응된다. (※ 이 규칙은 **5개 유형 전체 공통** — 모든 유형 MD에 동일 적용)
- **RULE 워크스페이스/콘솔 유형은 라이트 모드가 기본.** 데이터 밀도 높은 화면(표·수치·필드 다수) 가독성 우선. 상단바 토글로 다크 전환은 여전히 제공하되, 진입 시엔 무조건 라이트로 표시(페이지 마운트 시 라이트 강제).
- **PREFER** 라이트 배경 + 흰 카드(`surface/elevated`) + **민트 액센트는 실행·주요 액션에만**(`primary/main`) + **텍스트·아이콘 강조는 `text-accent-solid`** (라이트/다크 양방향 대응, playbook 1.1 상속). 나머지는 차분하게.
- **PREFER** 좌측 nav는 **얇은 아이콘 바**(메뉴 최소 — 작업 방해 안 함). 워크스페이스는 nav를 자랑하지 않는다.
- **PREFER** 결과/코드/JSON 블록은 `surface/sunken` 위 모노스페이스, 원문 프리뷰는 `surface/secondary` 카드.
- **AVOID** 결과를 근거 없이 raw JSON만 덤프. 최소한 구조화 뷰/표로 정리.

### 3.1 섹션 구분 — divider vs 흐름

> **원칙:** chrome · sticky · 사이드 패널 = divider. 콘텐츠 흐름 = divider 없음. bg 로 섹션 구분 금지.

- **RULE 콘텐츠 흐름 안의 섹션은 divider 금지 + bg 차이 금지.** 우측 캔버스처럼 "입력→처리→결과→후속 동선"이 한 흐름으로 읽혀야 할 때, 섹션 사이에 `border-b` / 배경색 밴드 넣지 않는다. 위계는 **여백(padding/gap)** 과 **텍스트 크기** 로만 표현. → 밴드가 들어가면 "다른 페이지 조각들이 붙어있는" 느낌이 되어 결과의 몰입감이 깨진다.
- **RULE chrome 성격 요소는 divider 필요.** 다음 4가지는 `border-{t,b,l,r} border-outline-{subtle,default}` 로 콘텐츠와 분리한다:
  1. 상단바 (top-bar) 하단
  2. 좌측 nav (아이콘 바) 우측
  3. 좌측 source/설정 패널 우측 (콘텐츠 캔버스와의 경계)
  4. **sticky 액션바 상단** (하단 고정 footer)
- **RULE 사이드 패널 내부 subsection 은 divider 필요.** 좌측 source 패널 안 "원본 이미지 / 처리 결과 / 비고" 같은 서로 다른 정보 카테고리 사이, AI 슬라이드 패널의 "헤더 / 본문 / 입력" 사이는 `border-b border-outline-subtle` 로 명확히 구분.
- **PREFER** divider 색은 대부분 `outline/subtle`. 강한 chrome 경계(top-bar, 사이드 패널 우측)만 `outline/default`.
- **AVOID** `bg-background-secondary` 같은 배경 밴드로 섹션 구분. 카드 내부 강조는 카드 자체의 `border` 로 이미 표현됨.

## 4. 모션 · 인터랙션 (절제)

- **RULE 모션 구현은 `motion-dev-animations` 스킬을 사용한다.** Motion.dev 기반이라 성능(GPU·60fps)·`prefers-reduced-motion`이 자동 처리된다. 타이밍·이징의 취향 기준은 `animation-systems` 스킬을 참고한다. (※ 두 스킬이 설치돼 있어야 함 — 미설치 시 사용자에게 알림)
- **PREFER** 처리중 → 완료 전환 시 결과를 **stagger로 부드럽게 등장**(위→아래 순차). 스트리밍이면 토큰/행 단위로 채워지게.
- **PREFER** 업로드 존 **drag hover 피드백**(테두리·배경 강조), 파일 드롭 시 상태 즉시 반영.
- **PREFER** 우측 AI 패널은 **슬라이드 인**(200~250ms, ease-out).
- **RULE** `prefers-reduced-motion` 존중 — 큰 이동·자동재생은 reduce 시 즉시 표시로. (playbook 1.9 상속)
- **AVOID** 장식용 3D·파티클·무한 루프 모션. 워크스페이스는 "차분한 제품 모션"이지 쇼가 아니다.

## 4.5 비주얼 크래프트 (선택 — 밋밋함 방지, **DS 준수 필수**)

> 색·레이아웃은 그대로 두고 "질감·깊이·폴리시"만 은은하게 더한다. 색을 바꾸는 크래프트는 금지.

### 표면 폴리시 (깊이 · 엣지)

- **PREFER** 카드·패널 깊이감을 레이어드 그림자로 살린다 (`beautiful-shadows`). ⚠️ **단 임의 그림자값을 코드에 직접 쓰지 말 것** — playbook "shadow 토큰만" 규칙 위반. 더 풍부한 elevation이 필요하면 **DS에 shadow 토큰으로 추가한 뒤** 사용(dana 문의).
- **PREFER** 주요 표면(업로드·결과 카드) 상단 엣지에 미묘한 그라데이션 하이라이트 (`css-border-gradient`, 색은 `primary`/`outline` 토큰만). 은은한 프리미엄 엣지 정도, 과하지 않게.

### 데이터 시각화 (이 유형의 핵심 레버)

- **PREFER** 워크스페이스 결과가 데이터(표·수치·집계)라면 `dataviz` / `naksha:chart-design` 스킬로 차트·구조화 뷰를 다듬는다. **결과가 데이터인 유형이라 여기가 "결과가 잘 보이냐"를 가르는 핵심 레버.**
  - 팔레트는 반드시 DS semantic 토큰(민트 계열 `primary/*`, `status/*` 등) 안에서 세팅 — Recharts/D3 등 라이브러리에 임의 hex 색 직접 박지 말 것.
  - 값 강조 vs 배경 위계는 semantic 토큰(`text/primary` vs `text/tertiary`, `primary/main` vs `outline/subtle`)으로.

### 일러스트 · 아이콘 · 스팟 아트

- **PREFER** empty state("아직 업로드된 문서가 없어요") · 상태 아이콘 · 결과 라벨 옆 spot 아트는 `naksha:illustration-system`으로 **일관된 커스텀 세트**를 쓴다. 밋밋한 기본 lucide 아이콘만 반복 배치하면 도메인 개성이 안 생긴다.
  - 색은 DS 토큰 안에서 (`primary/main` 액센트 + `text/tertiary` 라인 정도).
  - 스팟 아트 크기는 "빈 상태를 위로하는 정도" — 결과 캔버스 안에서 결과 위로 튀지 않게 절제.

### 워크스페이스에선 대개 불필요 (배경·텍스처·블러 계열)

- **AVOID** 노이즈·메시 그라데이션 등 `algorithmic-art` 계열 배경 텍스처. 두원 PoC 검증(2026-07) 결과: 데이터 밀도 높은 워크스페이스 캔버스 위에 얹으면 "은은한 광채"가 아니라 "왜 뭉개져 있지" 로 읽힘. 결과가 주인공인 유형에 어울리지 않음 → **랜딩·마케팅 유형에서 다룰 것**.
- **AVOID** 블러 · 강한 앰비언트 글로우 · 다층 색상 fog. **작업 방해.** `progressive-blur` 같은 강한 depth 효과는 **랜딩·마케팅 유형에서 더 적극적으로**, 워크스페이스 화면에선 **대개 불필요**.
- **PREFER** 배경은 solid `background/primary`(라이트: 흰, 다크: 최심), depth 는 카드·divider·shadow 토큰(3.1절 "섹션 구분") 으로만 만든다.

### 공통 AVOID

- **AVOID** 색을 바꾸는 크래프트, 요란한 글로우, 여러 효과 동시 남발. 크래프트는 "은은한 폴리시"지 장식이 아니다.

## 5. AVOID — anti-slop (워크스페이스에서 거부/교체)

- ❌ 하드코딩 색(`bg-zinc-900`·`text-indigo-700` 등) — seragem 실제 사례. → semantic 토큰. (playbook 1.1)
- ❌ 처리 상태를 안 보여주고 결과만 툭 — Empty/처리중 상태 없이 빈 화면.
- ❌ 결과를 raw JSON 덤프로만, 근거·원문 대조 없이.
- ❌ 입력이 어디인지 불분명(작은 버튼 하나) — 진입을 크게.
- ❌ dark + 다색 카드그리드 + 보라 그라데이션(제네릭 AI 슬롭 톤).
- ❌ nav 사이드바에 메뉴 잔뜩 — 여긴 어드민이 아니다, 작업에 집중.
